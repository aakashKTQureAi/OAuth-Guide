## Practical configuration path

The developer needs an Atlassian account able to access the developer console, a Jira Cloud site and user suitable for the intended test, the intended API operations, and a reachable application callback. Atlassian recommends 3LO for most direct integrations. API scopes set the maximum access; the authorizing user's Jira permissions still constrain each operation. No blanket Jira-admin prerequisite was established for creating the Cloud integration. [Security guide](https://developer.atlassian.com/cloud/jira/platform/security-for-other-integrations/), [Cloud guide](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#determining-the-scopes-required-for-an-operation).

1. **Create:** open [Developer console](https://developer.atlassian.com/console/myapps/), choose **Create → OAuth 2.0 integration**, and enter a name. Choose the grant type described below. [Creating apps](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#creating-oauth-2-0-3lo-apps).
2. **Grant boundary:** current documentation offers account-level grants, where consent can cover multiple installed sites, or resource-level grants limited to the selected site(s). This is a meaningful decision to explain before configuration. No source established whether this choice can later be changed. [Creating apps](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#creating-oauth-2-0-3lo-apps).
3. **Permissions:** under **Permissions**, add the relevant Jira API; use **Configure** to add only scopes required by the intended endpoints. Read each endpoint's OAuth scopes field. Atlassian recommends classic scopes where available; granular scopes support narrower operations. Do not supply a default broad scope bundle before learning the user's actions. Unsupported 3LO endpoints remain unavailable. Changing configured scopes requires existing users to consent again. [Scope catalog](https://developer.atlassian.com/cloud/jira/platform/scopes-for-oauth-2-3LO-and-forge-apps/), [endpoint selection](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#determining-the-scopes-required-for-an-operation).
4. **Callback:** **Authorization → Configure** beside OAuth 2.0 (3LO), enter **Callback URL**, and save. The later `redirect_uri` must match. The page does not settle localhost/HTTPS eligibility beyond requiring a URL accessible by the app. [Enable OAuth](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#enabling-oauth-2-0-3lo).
5. **Client credentials:** obtain Client ID and Secret from **Settings**. The documented code exchange requires the secret. Implementation guidance: keep secrets and tokens in an appropriate backend secret store; never ask guide users to paste them into research/chat. [Code exchange](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#2-exchange-authorization-code-for-access-token).
6. **Consent:** redirect the user to `https://auth.atlassian.com/authorize`, including `audience=api.atlassian.com`, `client_id`, space-separated configured `scope`, matching `redirect_uri`, unguessable session-bound `state`, `response_type=code`, and `prompt=consent`. Verify returned state before associating the callback with the user. Add `offline_access` only if refresh tokens are needed. [Authorize](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#1-direct-the-user-to-the-authorization-url-to-get-an-authorization-code).
7. **Exchange:** after successful consent the callback receives `code`. POST JSON to `https://auth.atlassian.com/oauth/token` with `grant_type=authorization_code`, `client_id`, `client_secret`, `code`, and matching `redirect_uri`. Check the response's token, expiry, and scopes; do not assume a fixed access-token lifetime. [Exchange](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#2-exchange-authorization-code-for-access-token).
8. **Find and test the site:** bearer-authenticated GET `https://api.atlassian.com/oauth/token/accessible-resources`; select the intended site's returned `id` as `cloudid`. Then make a permitted read-only call to `https://api.atlassian.com/ex/jira/{cloudid}/{api}` with the access token. Choose the test endpoint from the requested operations and its required scopes; no universal test endpoint was assumed. Returned resources indicate token site/scope access, not the user's complete Jira permissions. [API calls](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#3-make-calls-to-the-api-using-the-access-token).
9. **Refresh when needed:** with `offline_access`, exchange the refresh token at the same token endpoint using `grant_type=refresh_token`, Client ID, Secret, and refresh token. Store the newly returned refresh token in place of the previous one. Documented defaults are 90-day inactivity expiry and 10-minute reuse leeway. Reauthorization is needed when the grant/token becomes unusable. [Refresh tokens](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#how-do-i-get-a-new-access-token-if-my-access-token-expires-or-is-revoked).

## Sharing, approval, and blockers

Creation produces a private app usable only by its creator. **Distribution → Enable sharing** allows sharing authorization URLs with other users. They still perform consent. Sharing does not mean Marketplace listing or Atlassian approval. Unreviewed integrations show a warning. The main guide links a review route and explicitly says an informational Marketplace listing is not required to submit for approval. No review timeline or actual approval was established. [Distribution](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#distributing-your-oauth-2-0-3lo-apps).

The developer guide contains newer grant-specific sections alongside an older FAQ saying only one account grant exists. For a guide, explain current account/resource options and use the current token's `accessible-resources` result; do not promise every token reaches every site. Source wording should be checked again before publishing and the console UI has not been exercised.

Atlassian's policy warning addresses apps that collect API tokens or instruct customers to create individual 3LO apps. Its stated best practice is **one distributable app for the integration**. For an OAuth guide, distinguish a developer creating their own integration from a third-party vendor making every customer create separate OAuth apps. Do not turn this into a claim that all internal app creation is forbidden, or that every educational setup guide violates policy. Underlying legal-policy text and enforcement outcomes were not independently audited. [Official integration guidance](https://www.atlassian.com/blog/developer/building-secure-and-scalable-integrations-our-guidance-for-third-party-apps), [Cloud guide notice](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/#overview).

Unresolved inputs: intended API actions/scopes; internal versus distributable integration; account-level versus site restriction preference; actual callback environment; tenant policies; live consent and API behavior. Source-backed configuration is not console-tested configuration or approval-granted status.
